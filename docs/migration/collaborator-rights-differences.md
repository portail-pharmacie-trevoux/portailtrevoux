## Règles transversales

- Le rôle admin donne accès aux univers dans les deux security.mjs. Collaborateurs/RH et modification du planning restent réservés aux administrateurs ; aucune correction proposée ne doit accorder ces droits aux salariés.
- Seule différence de canAccess : main bloque le rôle spécial tester ; Scalingo ne gère pas ces comptes de démonstration séparés. Ils ne doivent pas entrer dans le périmètre des 16 users salariés.
- Pour un salarié avec permissions_configured=true, droit de consultation présent et edit_rights absent pour le module, main autorise implicitement la modification dans **Laboratoires, Commandes, Merchandising, Démarche qualité** ; Scalingo la refuse. Avec un edit_right explicite, ou un profil non configuré bénéficiant déjà du droit implicite, cet écart de helper n'existe pas. Il faut aussi tenir compte des gardes propres à chaque opération.
- La passerelle scalingoUniverseBoundary exige, avant une écriture dans les préfixes qu'elle couvre, canModify en plus de canAccess. Elle peut donc refuser une opération personnelle que le serveur main protégeait par consultation et propriété seulement. Une simple copie des tableaux rights/edit_rights ne neutralise pas cet écart.
- La passerelle refuse les API non déléguées explicitement. Les helpers spécifiques délèguent au serveur complet sans supprimer ses protections. Un rôle admin ne contourne pas les restrictions de prévisualisation ou la limitation de certaines routes à Administrateur Test.
